## Project structure

Create one Railway project per environment. Each project contains:

1. **Backend service** — Django API
2. **Frontend service** — Vite static site
3. **Collab service** — Node.js WebSocket server
4. **PostgreSQL** — Railway Postgres plugin

Connect the Railway project to the `paulvanderheijden/vector` GitHub repository. Each service uses a different root directory from the same repo.

## PostgreSQL

Railway provides managed PostgreSQL as a built-in database service. Each environment gets its own isolated Postgres instance.

### Adding the database

1. In the Railway project dashboard, click **+ New** → **Database** → **Add PostgreSQL**
2. Railway provisions a Postgres instance and exposes connection variables automatically

### Connection variables

Railway generates several variables on the Postgres service. The most important is `DATABASE_URL`, which contains the full connection string.

Reference it in the backend and collab services using Railway's variable references:

```
DATABASE_URL = ${{Postgres.DATABASE_URL}}
```

Other available variables (auto-generated, rarely needed directly):

| Variable | Example |
|---|---|
| `PGHOST` | `roundhouse.proxy.rlwy.net` |
| `PGPORT` | `28456` |
| `PGUSER` | `postgres` |
| `PGPASSWORD` | (auto-generated) |
| `PGDATABASE` | `railway` |

### Django configuration

The backend reads `DATABASE_URL` using `dj-database-url` in `settings.py`:

```python
import dj_database_url

DATABASES = {
    "default": dj_database_url.config(default="sqlite:///db.sqlite3")
}
```

This falls back to SQLite locally when `DATABASE_URL` is not set.

### Backups

Railway Postgres includes automatic daily backups with 7-day retention. For additional safety:

- Enable **point-in-time recovery** in the Postgres service settings (available on Pro plan)
- Before destructive migrations, create a manual backup via the Railway dashboard

### Seeding

After the first deploy to a new environment, run the seed command locally using the **public** Postgres URL (found on the Postgres service's Variables tab as `DATABASE_PUBLIC_URL`):

```bash
cd backend
DATABASE_URL="<DATABASE_PUBLIC_URL>" python manage.py seed
```

<Note>
  `railway run` injects environment variables but runs locally — the internal hostname (`postgres.railway.internal`) is not resolvable from your machine. Use the public URL instead.
</Note>

This populates the database with mock data (15 users, 6 circles, 31 decisions, 37 commitments, 18 sessions, 27 updates).

## Backend service (Django)

### Settings

| Setting | Value |
|---|---|
| Root directory | `/backend` |
| Build command | `pip install -r requirements.txt && python manage.py collectstatic --noinput` |
| Pre-deploy command | `python manage.py migrate` |
| Start command | `gunicorn vector.wsgi:application --bind 0.0.0.0:$PORT` |

<Warning>
  `migrate` must run as a **pre-deploy command**, not in the build command. The internal Postgres hostname (`postgres.railway.internal`) is only resolvable at runtime, not during the build phase.
</Warning>

### Environment variables

| Variable | Value | Notes |
|---|---|---|
| `DATABASE_URL` | `${{Postgres.DATABASE_URL}}` | Auto from Railway Postgres plugin |
| `SECRET_KEY` | (generate a strong random key) | Used for Django signing and JWT |
| `DEBUG` | `False` | Always `False` in deployed environments |
| `ALLOWED_HOSTS` | `.up.railway.app` | Django subdomain wildcard (dot prefix, not `*`) |
| `FRONTEND_URL` | `https://vector.up.railway.app` | Used for CORS `Access-Control-Allow-Origin` |
| `RESEND_API_KEY` | (from Resend dashboard) | For transactional emails |

### Security headers

When `DEBUG=False`, Django automatically enables production security headers:

| Header | Setting | Value |
|---|---|---|
| `Strict-Transport-Security` | `SECURE_HSTS_SECONDS` | 1 year, includes subdomains, preload |
| `X-Content-Type-Options: nosniff` | `SECURE_CONTENT_TYPE_NOSNIFF` | `True` |
| SSL redirect | `SECURE_SSL_REDIRECT` | `True` |
| Proxy SSL header | `SECURE_PROXY_SSL_HEADER` | `X-Forwarded-Proto: https` (Railway's proxy) |
| Secure cookies | `SESSION_COOKIE_SECURE` / `CSRF_COOKIE_SECURE` | `True` |

These are configured in `settings.py` and gated behind `not DEBUG` so local development is unaffected.

A custom `SecurityHeadersMiddleware` adds headers to all responses (both dev and prod):

| Header | Value |
|---|---|
| `Content-Security-Policy` | `default-src 'none'; frame-ancestors 'none'` |
| `Referrer-Policy` | `strict-origin-when-cross-origin` |
| `Permissions-Policy` | `camera=(), microphone=(), geolocation=()` |

### Static files

The backend uses **WhiteNoise** (already in `requirements.txt`) to serve static files. `collectstatic` runs as part of the build command.

## Frontend service (Vite)

### Settings

| Setting | Value |
|---|---|
| Root directory | `/frontend` |
| Build command | `npm install && npm run build` |
| Start command | `npx serve dist -s -l $PORT` |

### Environment variables

| Variable | Value | Notes |
|---|---|---|
| `VITE_API_URL` | `https://vector-api.up.railway.app` | Backend's public URL (no trailing slash) |
| `VITE_COLLAB_WS_URL` | `wss://vector-collab.up.railway.app` | Collab's public URL, must use `wss://` |

<Warning>
  Vite environment variables are **build-time only**. They are baked into the JavaScript bundle during `npm run build`. Changing them requires a redeploy.
</Warning>

## Collab service (Node.js)

### Settings

| Setting | Value |
|---|---|
| Root directory | `/collab` |
| Build command | `npm install && npm run build` |
| Start command | `npm start` |

The start command runs `node dist/server.js` (defined in `package.json`).

### Environment variables

| Variable | Value | Notes |
|---|---|---|
| `DATABASE_URL` | `${{Postgres.DATABASE_URL}}` | Same Postgres instance as backend |
| `JWT_SECRET` | `${{backend.SECRET_KEY}}` | Must match backend's `SECRET_KEY` for JWT validation |
| `PORT` | (auto from Railway) | Railway injects this automatically |

## Custom domains

For production, configure custom domains in Railway's service settings:

| Service | Domain |
|---|---|
| Frontend | `app.vector.com` |
| Backend | `api.vector.com` |
| Collab | `collab.vector.com` |

Add the domains to the backend's `ALLOWED_HOSTS` and update `FRONTEND_URL`, `VITE_API_URL`, and `VITE_COLLAB_WS_URL` accordingly.

## Health checks

Configure Railway health checks for the backend and collab services:

| Service | Health check path | Protocol |
|---|---|---|
| Backend | `/api/v1/health/` | HTTP |
| Collab | (none — WebSocket server) | TCP |
