This section covers the technical architecture and implementation details of the Vector frontend.

## Tech stack

| Layer | Technology |
|---|---|
| **Framework** | React 19 with TypeScript |
| **Routing** | React Router 7 |
| **UI Components** | shadcn/ui (Radix + Tailwind CSS 4) |
| **Data Tables** | TanStack React Table |
| **Rich Text Editor** | TipTap (with tiptap-markdown for serialization) |
| **Drag & Drop** | @dnd-kit |
| **Icons** | Lucide React |
| **i18n** | react-i18next + i18next (bundled JSON, EN + NL) |
| **Build** | Vite 7 |

## Project structure

```
src/
├── App.tsx              # Shell: sidebar + sticky header + scroll area + Outlet
├── main.tsx             # React Router config (all routes)
├── components/
│   ├── ui/              # shadcn primitives (button, badge, data-table, etc.)
│   └── *.tsx            # Shared feature components (28 total)
├── i18n/
│   ├── index.ts         # i18next config (bundled resources, fallback to "en")
│   ├── en.json          # English translations
│   └── nl.json          # Dutch translations
├── pages/               # One file per screen (15 total)
├── hooks/               # usePageHeader, use-mobile
└── lib/
    ├── api.ts             # Axios client with JWT interceptor
    ├── auth.ts            # login, logout, getMe, updateMe, getWorkspaces
    ├── auth-context.tsx   # AuthProvider + useAuth hook
    ├── services/          # React Query hooks (people, circles, decisions, etc.)
    ├── workspace-context.tsx # Workspace provider + useWorkspace hook
    └── utils.ts           # cn() classname helper
```

**Convention:** `components/` holds shared components used across multiple pages. If a component is only used by a single page, it should live in a `components/<PageName>/` subfolder (e.g. `components/Strategy/TableOfContents.tsx`). This keeps shared components flat and discoverable while preventing the directory from growing with page-specific concerns.

## Design principles

- **Match Linear's density** — data-dense, keyboard-friendly, fast
- **Light mode only** (V1)
- **shadcn Figma kit** as the design source of truth
- **Inline editing** — titles, summaries, and properties are editable in place (TextField + PropertySelect)
- **Consistent page headers** — every page injects its header via `usePageHeader` hook into the App shell's sticky header area

## Key architecture decisions

- **React Query for server state** — all data fetching uses per-entity hooks (`useDecisions`, `useCircles`, etc.) backed by React Query. No local mock data stores.
- **Multi-workspace context** — `WorkspaceProvider` stores the active workspace slug and exposes it via `useWorkspace()` hook. All API calls include the workspace slug in the URL path.
- **i18n with react-i18next** — all UI strings use `t()` calls with flat dot-separated keys (e.g. `sidebar.inbox`, `decision.status`). Translations are bundled as JSON. The user's language preference is stored on the backend (`User.ui_language`) and synced on login.
- **Page header via Outlet context** — pages don't render their own headers. Instead they call `usePageHeader()` which passes header JSX up to the App shell via React Router's Outlet context. This keeps the sticky header outside the scroll area.
- **Detail sidebar is per-page** — each detail page renders its own fixed-position `<aside>`. There is no shared DetailSidebar wrapper component; only the inner `SidebarSection` and `PropertiesRow` primitives are shared.

## Performance optimizations

### Code splitting

All workspace page components are **lazy-loaded** via `React.lazy` in `main.tsx`. Vite produces separate chunks per route, so the initial bundle only includes the shell (sidebar, header, router) plus the authentication pages. The `MarkdownEditor` (which pulls in Tiptap, Yjs, and Hocuspocus) is further isolated behind a `LazyMarkdownEditor` wrapper so editor dependencies are only loaded when an editor is first rendered.

### Memoization

The codebase applies targeted memoization at three levels:

- **Context stability** — `WorkspaceProvider` wraps its context value in `useMemo` and uses refs for values that shouldn't trigger re-renders (e.g. `pathname`), preventing cascade re-renders on navigation.
- **Field components** — all `*Field` components used in table rows (`StatusField`, `PersonField`, `DateField`, `HealthField`, `CircleField`, `DecisionField`, `SessionField`) are wrapped in `React.memo`. These render N times per table, so memo prevents re-renders when the parent re-renders but the field's props haven't changed.
- **Table columns** — `useMemo` wraps `makeColumns()` calls in `DecisionsTable` and `CommitmentsTable` so TanStack Table doesn't rebuild its column model on every render.
- **List view rows** — `DatabaseView`'s `ListRow` component is memoized with `useCallback` click handlers, so rows only re-render when their item data changes.
- **Derived data** — filter/sort results and computed values (e.g. `circleOptions`, `owners`, `initiativeMap`) are wrapped in `useMemo` in list pages to avoid recomputing on unrelated state changes.

### React Query tuning

- **`staleTime: 5 minutes`** — set globally on the `QueryClient`. Prevents background refetches during normal navigation. Data is still refetched on window focus and after mutations.
- **`enabled` flags** — list hooks (`useSessions`, `useCommitments`) accept an `enabled` option so detail pages can skip fetches until prerequisite data loads. For example, `DecisionDetail` only fetches commitments once the decision has loaded.
- **Narrow invalidation** — mutations use `refetchType: "none"` for list queries when only the detail cache needs updating (via `setQueryData`). Create mutations use `refetchType: "active"` so only visible lists refetch.

### Mutation cache strategy

All entity update mutations use `setQueryData` to write the API response directly into the React Query detail cache, avoiding a refetch for the single-entity view. List queries are invalidated with `refetchType: "none"` so they refetch lazily on next access rather than immediately.

### Token refresh deduplication

The Axios response interceptor deduplicates concurrent 401 refresh attempts by sharing a single `refreshPromise`. Parallel requests that hit a 401 all await the same token refresh instead of each triggering their own.
